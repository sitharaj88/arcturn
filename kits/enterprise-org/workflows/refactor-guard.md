---
name: refactor-guard
description: Characterization tests first and green at HEAD, then a partitioned behaviour-preserving refactor, then a drift hunt. A refactor whose oracle is written afterwards has no oracle.
stepTimeoutMs: 1800000
continueOnError: false
budgetUsd: 30
---
Run it as `/workflow refactor-guard <the invariant you are trying to enforce
and the target shape>`.

One rule decides whether this pipeline is worth running: the characterization
tests are written before the refactor starts and they must pass at HEAD. A
suite written after the change describes the change; a suite written before it
describes the behaviour the change must preserve. Only one of those is an
oracle, and stage 2 halts if it cannot produce one.

Refactors are the highest-risk engagement class for scope creep, so the budget
ceiling is hard and any request to widen a lane's scope is an automatic stop
rather than a negotiation. If the refactor turns out to require changing a
declared invariant, that is an architecture change and it belongs in
feature-build with the architect and a human gate, not here.

Stage 6 exists because a characterization suite only pins the behaviour
somebody thought to characterize. The drift hunt goes looking for the behaviour
nobody pinned.

Stages 2, 4 and 5 dispatch `qa-functional` and `developer`, both of which carry `write`/`edit` on top of `bash`, so all five of those steps run on the **write lane**: each in its own detached worktree, seeded with the run's state so far, diff captured to a patch, replayed into your real checkout with a plain `git apply`. Stage 4's two branches are two separate worktrees over the plan's two disjoint module scopes, so they can never collide even though they share a role. Stage 6's `qa-adversarial` carries `bash` alone, with neither `write` nor `edit`, so it runs on the **exec lane** instead: the same worktree isolation so it can actually run the drift hunt, but with an unconditional guarantee rather than an expectation — whatever it does in that worktree is never captured and never applied, and the engine appends `ARCTURN-PATCH: status=discarded` to its output itself, regardless of what the step's own text says. `architect` and `tech-lead` are the only roles in this pipeline with no mutating tool at all, and are the only two that run on the fresh-context **read lane** — no worktree, nothing to execute. Plan mode has no write lane: stage 2 fails immediately, before a token is spent, if the parent session is in plan mode.
